# خطة إعادة بناء نظام التسعير ولوحة الإدارة

## الهدف
جعل قاعدة البيانات المصدر الوحيد لكل ما يظهر في بطاقة الأسعار، وإلغاء الاعتماد على نصوص وأسعار ثابتة داخل `ratecard.html`. عند الحفظ من لوحة الإدارة يتأكد النظام من نجاح الكتابة، ثم تتحدث المعاينة والصفحة الرئيسية المفتوحة فوراً، وتصل التغييرات إلى الزوار الآخرين لحظياً.

## سبب المشكلة الحالي
- الصفحة الرئيسية تعرض ملف HTML ثابتاً داخل `iframe`، بينما لوحة الإدارة تطبيق React منفصل؛ لا توجد حالة بيانات مشتركة بينهما.
- رسالة التحديث الحالية تُرسل فقط إلى معاينة داخل لوحة الإدارة، ولا تصل إلى الصفحة الرئيسية المفتوحة في تبويب آخر أو إلى الزوار.
- لا يوجد اشتراك لحظي بتغييرات جدول الأسعار؛ التحديث يعتمد على إعادة الجلب عند التحميل أو العودة للتبويب.
- الأسعار الإقليمية مستنتجة من كلمات داخل الاسم والملاحظة، وبعض أسعار عمّان تُستخرج من نص الملاحظة ثم تستبدل السعر؛ لذلك قد تعيد منطق المنطقة كتابة القيمة المحفوظة.
- نجاح طلب `update` لا يثبت حالياً أن صفاً تم تعديله فعلاً، كما لا توجد نسخة/سجل تغييرات أو استرجاع.

## المرحلة 1 — نموذج بيانات صريح وآمن
1. تطوير بنية بنود التسعير لتحتوي حقولاً صريحة بدلاً من تحليل النص:
   - المنطقة: إربد، عمّان، أو كلتاهما.
   - القسم/الخدمة والترتيب.
   - الاسم والوصف والشارة بالعربية والإنجليزية.
   - حد السعر الأدنى والأعلى، العملة، والوحدة بالعربية والإنجليزية.
   - الملاحظة أسفل السعر بالعربية والإنجليزية.
   - الحالة: ظاهر/مخفي، وبند مميز.
2. ترحيل البنود الحالية دون فقد أي أسعار أو نصوص، مع تحويل نطاقات السعر الحالية إلى قيم منظمة.
3. إضافة جدول سجل تغييرات للتسعير يحفظ البند، القيم السابقة والجديدة، المدير، ووقت التعديل، مع سياسات وصول للمدير فقط.
4. تفعيل بث تغييرات بنود التسعير لحظياً، مع الإبقاء على القراءة العامة الآمنة والكتابة للمدير فقط.

## المرحلة 2 — طبقة بيانات واحدة وموثوقة
1. إنشاء نماذج تحقق للمدخلات تمنع النطاقات المعكوسة والقيم غير الصالحة والنصوص المفرطة.
2. نقل الحفظ الإداري إلى وظائف خادم محمية تتحقق من هوية المدير وصلاحياته، تنفذ التعديل وسجل التغيير في عملية واحدة، ثم تعيد الصف المحفوظ فعلياً.
3. إنشاء جلب عام موحد لبنود التسعير الظاهرة فقط، بترتيب ثابت وحقول آمنة محددة.
4. إضافة مفاتيح استعلام موحدة وتحديث متفائل مع رجوع تلقائي عند فشل الحفظ، ورسائل خطأ دقيقة بدلاً من إعلان نجاح غير مؤكد.

## المرحلة 3 — إعادة بناء الصفحة الرئيسية دون iframe
1. تحويل بطاقة الأسعار الحالية إلى مكونات React مع الحفاظ على التصميم والحركة والهوية الحالية.
2. جعل مكونات البطاقة ترسم مباشرة من بيانات قاعدة البيانات؛ لن يبقى أي سعر احتياطي قابل لأن يطغى على القيمة المحفوظة.
3. فلترة المنطقة بواسطة حقل `region` الصريح، لا بواسطة البحث عن “عمّان/إربد” داخل النص.
4. الحفاظ على رحلة: اختيار المنطقة ← اختيار الخدمة ← عرض الأسعار، واللغة العربية/الإنجليزية، وروابط واتساب والمعدات والموقع الرئيسي.
5. إضافة حالات تحميل، خطأ، وإعادة محاولة دون عرض أسعار قديمة أو شاشة فارغة.

## المرحلة 4 — لوحة إدارة شاملة
1. تنظيم لوحة الإدارة إلى تبويبات واضحة: نظرة عامة، الأسعار والخدمات، المعدات، الطلبات، التحليلات، وسجل التغييرات.
2. محرر تسعير تفصيلي لكل بند يتضمن:
   - المنطقة والقسم والترتيب.
   - جميع النصوص العربية والإنجليزية.
   - سعر ثابت أو نطاق أدنى/أعلى.
   - الوحدة والعملة والملاحظة.
   - إظهار/إخفاء وتمييز البند.
3. إضافة إنشاء بند، نسخه، حذفه حذفاً آمناً، إعادة الترتيب، البحث، التصفية حسب المنطقة والخدمة، وحفظ جماعي واضح.
4. معاينة فعلية داخل اللوحة مع اختيار المنطقة واللغة والخدمة، تعرض نفس مكوّن الصفحة الرئيسية وليس نسخة HTML مختلفة.
5. حالات احترافية: مؤشر تعديلات غير محفوظة، منع الخروج قبل الحفظ، تعطيل زر الحفظ أثناء الطلب، نجاح/فشل، وإظهار وقت آخر تحديث.
6. سجل تغييرات يسمح بمراجعة ما تغير ومن قام به واسترجاع نسخة سابقة بعد التأكيد.

## المرحلة 5 — التحديث الفوري الحقيقي
1. بعد نجاح الحفظ: تحديث بيانات لوحة الإدارة والمعاينة والصفحة الرئيسية في نفس التبويب فوراً دون إعادة تحميل.
2. استخدام قناة المتصفح لتحديث أي تبويب آخر مفتوح على الجهاز نفسه.
3. الاشتراك في بث قاعدة البيانات لتحديث صفحات الزوار المفتوحة عند أي تعديل منشور.
4. إضافة إعادة جلب احتياطية عند استعادة الاتصال أو العودة للتبويب؛ البث اللحظي ليس نقطة فشل وحيدة.
5. إظهار حالة المزامنة في لوحة الإدارة: محفوظ، جارٍ النشر، منشور، أو فشل.

## المرحلة 6 — التحقق والجودة
1. اختبار ترحيل جميع البنود الحالية ومقارنة السعر والنص والمنطقة قبل/بعد.
2. اختبارات منطقية للنطاقات، الفلترة الإقليمية، اللغة، الإخفاء، والترتيب.
3. اختبار متصفح شامل: تعديل سعر من لوحة الإدارة والتأكد أنه يتغير في الصفحة الرئيسية المفتوحة دون refresh؛ ثم إعادة التحميل والتأكد من بقاء القيمة.
4. اختبار تبويبين واختبار زائر منفصل للتأكد من وصول التغيير اللحظي.
5. اختبار الهاتف وسطح المكتب وعدم تداخل النصوص الطويلة أو النطاقات السعرية.
6. مراجعة صلاحيات القراءة والكتابة وسجل التغييرات، ثم فحص أخطاء المتصفح والشبكة.

## النتيجة النهائية
- لا `iframe` ولا أسعار ثابتة تتنافس مع قاعدة البيانات.
- تعديل واحد من لوحة الإدارة ينعكس فوراً على الرئيسية والمعاينة والتبويبات والزوار المفتوحين.
- كل تفاصيل البنود قابلة للإدارة بالعربية والإنجليزية مع مناطق ونطاقات واضحة.
- حفظ موثوق، سجل تغييرات، واسترجاع، مع اختبارات تمنع عودة المشكلة.

## تفاصيل تقنية
- الحفاظ على TanStack Start وReact Query ومكونات التصميم الحالية.
- استخدام وظائف خادم محمية لعمليات الإدارة، وقراءة عامة محدودة للتسعير المنشور.
- تطبيق تغييرات قاعدة البيانات عبر migration مع `GRANT` وRLS لكل جدول جديد.
- إزالة كود جلب الأسعار المباشر والمفتاح العام المضمّن من ملف HTML بعد اكتمال مسار React.
- عدم تغيير تصميم بطاقة الأسعار بصرياً إلا بالقدر المطلوب للحالات الجديدة والاستجابة للموبايل.
